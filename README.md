Тема: робота з даними на рівні бази, оптимізація запитів і коректна поведінка API при помилках.

Більшу частину матеріалу на занятті не розбирали - потрібно самостійно почитати документацію MongoDB та Mongoose. Вміння знайти відповідь у документації - така сама навичка, як і написання коду.

Працюємо з базою shopDB та проєктом з попереднього дз.

Формат здачі
Одне посилання на репозиторій на GitHub з усією роботою.

Що має бути в репозиторії:

Код проєкту (доопрацьований проєкт з попередніх дз)
Файл queries.md у корені - усі запити з Завдань 1 і 2 разом з результатами їх виконання та відповідями на теоретичні питання
Файл README.md з інструкцією: як встановити залежності, які змінні потрібні в .env, як запустити проєкт

Важливо: файл .env з реальним рядком підключення до бази не має потрапити в репозиторій. Додайте .gitignore з .env та node_modules. Якщо ви ще не працювали з .gitignore , то потрібно розібратися.

Результати запитів у queries.md оформлюйте як текст у блоках коду, копіюючи вивід з mongosh або Compass. Скріншоти не потрібні.

Завдання 1: Aggregation Pipeline
Погугліть, що таке aggregation pipeline і як працюють стадії $match, $group, $sort, $project. Зверніть увагу на акумулятори $sum, $avg, $max, $min та на те, що означає _id у стадії $group.

Виконайте запити у Compass (вкладка Aggregations) або в mongosh:

Порахувати кількість товарів у кожній категорії
Порахувати середню ціну товарів по кожній категорії
Знайти сумарну вартість складу — суму price * stock по всіх товарах
Вивести тільки ті категорії, у яких середня ціна більша за 300
Порахувати кількість активних та неактивних користувачів
У queries.md для кожного пункту наведіть сам pipeline і результат його виконання.

Підказка: у стадії $group поле _id - це те, за чим ви групуєте. Якщо потрібно порахувати щось по всій колекції без групування, передайте _id: null.

Завдання 2: Індекси та швидкість запитів
Дізнайтеся, що таке індекс у MongoDB, як він влаштований і чому прискорює пошук. Своїми словами (3–4 речення) опишіть у queries.md, у чому різниця між COLLSCAN і IXSCAN.
Виконайте db.products.getIndexes() та db.users.getIndexes(). У колекції users ви знайдете індекс, який не створювали вручну. Поясніть, звідки він узявся — підказка: шукайте у файлі userModel.js.
Виконайте запит з фільтром по category з .explain("executionStats") і збережіть значення totalDocsExamined, totalKeysExamined та stage.
Створіть індекс на поле category у колекції products.
Повторіть запит з .explain("executionStats"). Наведіть обидва результати поруч і порівняйте.
Спробуйте додати користувача з email, який уже існує в колекції. Наведіть текст помилки і поясніть, чому вона виникла.
Завершіть розділ висновком у 2–3 речення: як змінилася кількість переглянутих документів і чому.

Завдання 3: Нормальна обробка помилок в API
Зараз ваше API у частині випадків повертає статус 500 там, де мало б повертати 400 або 404. Виправте це.

Перевірте, що станеться при запиті GET /api/products/123abc - тобто з рядком, який не є валідним ObjectId. Розберіться, який саме тип помилки кидає Mongoose (шукайте CastError) і зробіть так, щоб API повертав статус 400 з осмисленим повідомленням, а не 500.
Додайте до моделі товару enum для поля category - дозволені значення electronics, books, clothing, food. Перевірте, що станеться при спробі створити товар з категорією toys.
Зробіть так, щоб при помилці валідації Mongoose API повертав статус 400 і список полів, які не пройшли перевірку, а не одне довге текстове повідомлення. Підказка: подивіться на структуру об'єкта error.errors.
Реалізуйте централізований error-handling middleware. Погугліть, чим він відрізняється від звичайного middleware - ключова відмінність у кількості аргументів функції. Після цього приберіть повторювані try/catch блоки з контролерів настільки, наскільки зможете.
Додайте middleware для неіснуючих маршрутів: запит на /api/nonexistent має повертати 404 у форматі JSON, а не стандартну HTML-сторінку Express.
У README.md додайте розділ «Обробка помилок»: перелічіть приклади запитів (метод, URL, тіло) і те, який статус та тіло відповіді має повернути ваше API для кожного з випадків 1, 2, 3, 5. Це має бути написано так, щоб перевіряючий міг взяти ваші приклади й відтворити їх у Postman.
